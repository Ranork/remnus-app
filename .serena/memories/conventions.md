## Auth
- NEVER call `auth()` directly in server actions/components — use `getCurrentUser()` from `src/lib/auth/session.ts` (React.cache wrapped)
- Workspace-locked project-window sessions (`npx remnus open`) are DENY BY DEFAULT: `auth()` returns null for them, `getCurrentUser()` throws. Only workspace-content code opts in via `getCurrentUserAllowingWorkspaceLock()` / `getSessionAllowingWorkspaceLock()` and must then call `assertWorkspaceLockAllows(user, resolvedWorkspaceId)` before any admin shortcut. Raw `authWithWorkspaceLock` is for `session.ts` only. The UI follows the same line: the `(app)` layout derives ONE `isProjectWindow` boolean from the lock claim and passes it to `WorkspaceSidebar` / `MobileNavWrapper` / `ActivityTracker` — never re-derived client-side. Everything that isn't workspace content is omitted in JSX (not CSS-hidden), so account-level server calls like `getUserAgentTokenCount` / `getMyTier` — both of which call `getCurrentUser()` and therefore throw here — never fire. See AGENTS.md → Project Install §4.
- All workspace actions → `assertWorkspaceAccess(workspaceId)`
- All database/page actions → `assertDatabaseAccess(databaseId)`
- Unauthenticated → `redirect('/login')`; unauthorized → throws

## Data Patterns
- JSON column pattern for dynamic properties (no EAV, no extra tables)
- `SelectOption`: `{ value: string; color?: SelectOptionColor; icon?: string }` (icon = emoji/`lucide:Name`/upload URL, same format as `PageIcon`; rendered via `PropertyTags.tsx`'s `OptionIcon`) — `normalizeOption` for backward compat with plain strings
- Date formatting: `formatDateValue()` from `properties.ts`; never hardcode `'en-US'`
- Bulk paste import (`BulkRowsDialog` → `bulkCreatePages`/`bulkUpdatePagesByMatch`): headers match column NAMES case-insensitively; unknown headers are dropped; unknown select/status values are auto-appended to the schema as new options. `content` is a RESERVED header (`CONTENT_HEADER`/`extractRowContent` in `propertyCoercion.ts`, added 2026-08-04) that writes the row's markdown BODY, not a property — unless the database has a real column named "Content", which wins. Omitted `content` leaves an existing body untouched (partial patch, same as the properties merge). `syncPageLinks` runs per row AFTER the transaction, never inside it. Use JSON not TSV/CSV for multi-line bodies; `MAX_BULK_ROWS` 500 and Next's default 1MB server-action body limit both apply

## Dashboards (added 2026-09-22)
- `workspace_items.type` is now `page | database | dashboard`. There is no DB CHECK, so the compiler is the only thing that finds the call sites — widen the TS union and let `npx tsc --noEmit` enumerate them. The full audit lives in `AGENTS.md` → **Dashboards**; don't redo it from scratch.
- The dashboard spec (`src/lib/dashboard/schema.ts`) is the single zod source of truth for renderer AND MCP writes. Never write a second schema for it. Blocks are addressed **by `id`, never by array index**, and carry a data SOURCE, never rows.
- Row filtering/sorting for BOTH database views and dashboard blocks lives in `src/lib/tableFilters.ts` (pure, no 'use client'). `DatabaseView.tsx` imports it — do not inline a copy back into a component.
- A dashboard route is server-rendered end to end: resolve block data in `src/lib/dashboard/data.ts`, never per-block client fetches.
- Every dashboard write (MCP tools AND web actions) goes through `src/lib/services/dashboards.ts` (`createDashboardInWorkspace` / `patchDashboard`). Don't add a second write path: it owns per-block validation of touched blocks only, reference normalization, compare-and-swap, and the `warnings` self-check. Keep block shapes OUT of MCP `inputSchema` (`z.array(z.any())`) — the catalog is the `remnus://dashboard/catalog` resource, generated from zod so it cannot drift.
- Service error text (`DashboardInputError`) is English and agent-facing; the web editor logs it and shows its own localized message.

## MCP / Agent Token Conventions
- Token format: `<MCP_TOKEN_PREFIX>_<prefix8>_<secret>` (env var `MCP_TOKEN_PREFIX=rmns`)
- Verification: look up by `tokenPrefix`, then `bcrypt.compare(secret, tokenHash)` — never iterate all tokens
- `/api/mcp` is whitelisted in `auth.config.ts` (`isMcpRoute`) so middleware never redirects MCP requests
- `export const runtime = 'nodejs'` required on MCP route (bcryptjs not Edge-compatible)
- Write tools must check `ctx.scope !== 'write'` and return an error — never execute the mutation
- Audit logs in `agent_activity` are best-effort (`.catch(() => {})` — tool response must not depend on audit success)
- **`/api/mcp` is stateless-only (as of 2026-08-03) — do not re-add a stateful SSE branch.** It used to also support a legacy stateful SSE transport (hand-rolled `SseCustomTransport` + `activeSseConnections` Map, for older Cursor/Windsurf/Continue/Antigravity configs: GET with `Accept: text/event-stream` opened a `ReadableStream` and handed back an `event: endpoint` handshake with a `sessionId`, later POSTs to `/api/mcp?sessionId=...` fed it). That stream was never closed server-side, so it idled on Vercel Fluid Compute until forced to the `maxDuration` ceiling, then the client reconnected and repeated — 785 "Task timed out after 300 seconds" errors in a single 24h window from only 7 tokens, and this was the dominant driver of the account's Fluid Provisioned Memory cost (confirmed: `query_audit_log` showed zero real successful tool calls through that path in the preceding week — only the already-existing stateless `WebStandardStreamableHTTPServerTransport` path had real traffic). Removed entirely rather than just bounding the duration, since audit data showed no real client depended on it. `maxDuration` lowered 300 → 60 as a backstop (real tool calls, including `bulk_update_pages`, finish in low seconds). If a user reports an old SSE-mode MCP client breaking, that's the known tradeoff — point them at the modern Streamable HTTP config for their client rather than reintroducing the unbounded stream.
- MCP tool `content` text blocks are compact `JSON.stringify(x)` (since 2026-07-08, no pretty-print) — `response_bytes` measures compact size.
- **MCP tool surface = a per-session token budget (re-measured 2026-09-22, `npm run bench:mcp-budget` → `src/scripts/mcp-token-budget.ts`, which supersedes `bench-mcp-overhead.ts`).** Only `description` + `inputSchema` reach the model — the Anthropic tools API has no output-schema field, and `annotations` are client-side hints — so those two carry only sentences that change agent behaviour (`update_page`'s merge semantics, `confirm: true`, `bulk_move_items`' all-or-nothing refusal); anything restating a field's own name is pure cost. `outputSchema`/`annotations` are wire-only and may stay descriptive. Measured: model-visible 31.0 KB → 21.7 KB write scope (~7,750 → ~5,410 tok), and read scope ~7,750 → ~1,360 tok because **`handler.ts` now registers `registerWriteTools` only when `ctx.scope === 'write'`** (they used to be advertised to every token and refused at call time — wasted context *and* misled the agent). Zod detail that matters: `z.string().uuid()` serialized a ~180-byte regex into all 14 write schemas (`contextRunId`); it is `z.string().max(64)` now, since the id is looked up anyway. `z.literal([-1,1,2,3,4])` emits a compact `enum` where `z.union([z.literal(-1), …])` emitted five `anyOf` branches.
- **Every tool returns the same JSON twice on purpose** — `content[0].text` AND `structuredContent` — and that is NOT redundancy to trim. Claude Code forwards only `structuredContent` to the model when both are present (anthropics/claude-code#55677, #79944); Claude Desktop and Cursor forward only the text block (blockscout/mcp-server#324 broke exactly by shortening the text after moving data into `structuredContent`). Each client forwards one copy, so the model-visible size is one copy — which is what `agent_activity.response_bytes` records. The MCP SDK also *refuses* a result without `structuredContent` once a tool declares `outputSchema`. Header comment in `tools/read.ts` carries this; read it before "optimizing" either half away.
- `query_database` row markdown bodies are OMITTED by default (opt-in flip 2026-07-08) — included only when `'content'` is in `fields`; single-row body via `get_page`. Agents querying the Work Plan should still pass a `fields` projection to trim columns; never bulk-request bodies across the whole Work Plan (≈15–20k tokens pre-flip, measured on prod audit logs)
- **`query_database` `filters` on scalar columns (select/status/text/number) were broken until 2026-08-05** — found via real MCP usage (Marketing Log `channel` filter threw `SQLITE_ERROR: malformed JSON`), independently reproduced against `local.db`. Root cause: the `json_each` branch fed it `json_extract(properties, path)`, which SQLite dequotes for scalar leaf values (`"Done"` → `Done`) — no longer valid JSON, so `json_each` chokes. `multi_select`/array filters were never affected (arrays aren't dequoted). Fix: source the `json_each` argument from the `->` operator instead (preserves JSON encoding), leave the equality branch on `json_extract` (dequoting is correct there). AGENTS.md's Work Plan section used to tell agents to work around this by listing all rows and filtering in memory — that workaround is now removed; if you see it resurface in a stale doc, the fix is real, prefer `filters` again.
- **`get_pages` (added 2026-08-05)** — batch counterpart to `get_page` for a specific, already-known, possibly cross-database/mixed-type ID list (`pageIds: string[]`, max 50; e.g. from `search_workspace`/`get_related_pages`/`get_changes_since`). Backed by `getPagesByIds` in `services/workspace.ts`, which deliberately uses `Promise.allSettled` — unlike `bulkUpdatePages`'s `Promise.all` — so one bad/inaccessible ID doesn't drop the rest of the batch; each result carries its own `ok`/`error`. Not a `query_database` replacement: when the IDs share one database, `query_database` with `filters`/`fields` is a single query and cheaper than N lookups — `get_pages` is for the heterogeneous-ID case that has no other one-call answer. Read tool count is now 11 (was 10) — re-measure with `bench-mcp-overhead.ts` when convenient (blocked locally 2026-08-05 by a missing `server-only` package, pre-existing/unrelated to this change).
- **`add_comment` (write, migration 0045)** — writes into the new `page_comments` table: a time-ordered comment thread on a page or database row, kept separate from its markdown body. Agent comments are append-only (no `update_comment`/`delete_comment` tool exists) so the thread stays a record of what an agent did rather than editable prose; only a human (comment author or workspace owner) can delete one, via the UI (`src/lib/actions/comments.ts`'s `deleteComment`, which re-checks the permission server-side regardless of what the client showed). `author_label` is denormalized at write time — same reasoning as `agent_activity.tokenId`/`oauthTokenId` (`ON DELETE SET NULL`) — so the byline survives token revocation. Read-side surface: `get_page`'s `includeComments` param (default false) and `query_database`'s per-row `commentCount` (one grouped query per page of results, same pattern as the `recurring: true` marker — absent when a row has zero comments). Service: `src/lib/services/comments.ts`. UI: `PageCommentsPanel.tsx`, mounted below `BlockEditor` and above `KnowledgeContextPanel` in both `PageEditor.tsx` and `StandalonePageEditor.tsx`. `page_comments.updated_at` is one branch of `computeChangeVersion` (moved 2026-09-21 from `/api/activity/ping` into `src/lib/services/changeVersion.ts`, shared with the new `GET /api/activity/changes`) — otherwise an agent's MCP `add_comment` call would never trigger a live `router.refresh()` for a human already viewing that page. Write tool count is now 11 (was 10).
- **`bulk_delete_pages`/`bulk_move_items` (write, migration 0047, 2026-09-01)** — per `.ai/FEATURE_BULK_AND_TRASH.md`, a direct request from Remnus's most active MCP user (Mitch), whose archiving script needed bulk ops and had already lost 11 rows once to `bulk_update_pages`'s silent `Promise.all` failure mode. Both new tools return `{requested, succeeded, failed, results: [{id, ok, error?}]}` via `Promise.allSettled` (same pattern as `get_pages`'s `getPagesByIds`, NOT `bulkUpdatePages`'s `Promise.all`) — one bad id in a batch of up to 100 never sinks the rest. `bulk_delete_pages` follows `delete_page`'s exact preview/confirm shape, batched; `bulk_move_items` takes exactly one of `newParentId` (batched sidebar reparent, same semantics as `move_item`) or `targetDatabaseId` (the genuinely new capability — moving database rows to a DIFFERENT database, which `move_item` never supported since it only reparents within the sidebar tree). The cross-database move refuses the WHOLE call up front if the target database's schema doesn't cover every source column by name AND type, naming the missing columns — a deliberately stricter check than the bulk-paste-import path (`propertyCoercion.ts`'s `coerceRowValues`, which auto-appends unknown option values); silently dropping a property here is exactly what the feature must not do. **Every delete now writes a full-content snapshot first** (`snapshotBeforeDelete` in the new `services/snapshots.ts`, best-effort like `recordDeletionTombstone`) — at all 4 existing hard-delete call sites, not just the two new bulk tools: `deleteItemFromWorkspace`/`deleteWorkspaceItemAndDescendants` (MCP), `deleteWorkspaceItemRecursive` (web sidebar), `deletePage` (web row delete). Deliberately excluded: the recurrence auto-prune path, since those rows are guaranteed content-empty by the recurrence dirty-occurrence invariant. Restore is **per-item, not per-subtree** (deleting a folder/database writes one snapshot per node, each restores independently) and **human-only — no MCP tool** (`actions/trash.ts`; an agent reviving something a human deliberately deleted would make the delete meaningless, same reasoning as `page_comments` agent writes being append-only). **UI is a sidebar-level `TrashModal.tsx`, NOT a Workspace Settings tab** (moved there post-launch per user feedback) — same "common ground" placement as `AgentsModal.tsx` (persistent sidebar button, cross-workspace: `getMyTrash()` mirrors `getUserWorkspacesWithTokens()`, grouped by workspace) since a delete can happen in any workspace and the entry point shouldn't be scoped to whichever one is active. Each entry carries a `breadcrumb: string[]` (ancestor titles, workspace name and the item's own title excluded) built by `listTrashForWorkspaces()` — walks the ancestor chain checking live `workspace_items` first, then falls back to a sibling snapshot if an ancestor was ALSO deleted; a row's breadcrumb resolves its (possibly also-deleted) database first via `page_snapshots.database_id`. 30-day retention, purged by the existing `/api/cron/recurrence` daily cron (no new scheduler, per the spec). Write tool count is now 13 (was 11); total 24. See `AGENTS.md` → **Trash & Version History** for the full write-up.
- **Content version history (Part C of the same spec, 2026-09-01, no new migration, no new MCP tool)** — `page_snapshots.reason='update'` rows, reusing the table B built. `maybeSnapshotContentUpdate()` (`services/snapshots.ts`) is called by all 4 content-write paths (`updateStandalonePageContent`/`updatePageContent` web autosave, `updatePageById` for MCP `update_page`/`bulk_update_pages` AND the write-share editor). Each fetches the row's content BEFORE overwriting and passes it as `priorContent` — the value actually stored (never the new content). Skip entirely if `newContent === priorContent` (autosave tick with no real change), regardless of actor. Otherwise: **human writes are debounced** (session+size threshold measured against the page's LAST snapshot, not the previous save — skip unless >10min elapsed OR the new content's length differs from the last snapshot's by >30%; no prior snapshot always creates a baseline one) so continuous typing collapses to ~3-8 versions/day instead of one per 1s autosave tick; **agent (MCP) writes never debounce** — every real change gets its own version. The debounced/not split is derived automatically from `actor.kind === 'human'` on `updatePageById`'s new `actor?: SnapshotActor` param (deliberately separate from the pre-existing `agentCtx?: {tokenId}`, which only feeds the unrelated `agentEditedAt`/`agentTokenId` columns and has no display name) — so the write-share path (`sharing.ts`, human, still debounced) and MCP writes (agent, never debounced) fall out of one rule. The OKF import route's post-import link-rewrite call passes no `actor` — no resolvable identity, not a meaningful edit — so `updatePageById` skips versioning rather than inventing a "system" actor. **Restore is itself a recorded version** (`restoreContentVersion()` snapshots the current live content first, non-debounced, before overwriting it) — human-only, no MCP tool, `actions/history.ts`. Two independent caps: **20 versions/page** enforced at write time (a page can accumulate versions indefinitely, unlike a delete snapshot which is naturally one-shot), **25MB/workspace total** (any `reason`) via `enforceWorkspaceSnapshotByteCaps()` on the same daily cron as trash cleanup — evicts oldest-first, bounded to 200 workspaces/run; the number is a judgment call the spec explicitly left open. The existing 30-day `purgeExpiredSnapshots()` (no `reason` filter) already covers version rows too. UI: `PageHistoryModal.tsx`, opened from a new "History" item in the existing "..." menu on both `StandalonePageEditor.tsx`/`PageEditor.tsx` (same menu as "View as Markdown") — NOT a persistent panel like `PageCommentsPanel`, used occasionally so it shouldn't cost every page permanent space. Shows a compact `+N/−M` character-delta per version (common-prefix/suffix trim, NOT a real diff — explicitly out of scope, same as trash). See `AGENTS.md` → **Trash & Version History** for the full write-up.
- **Local workspace map `.remnus/workspace-map.md` (2026-09-22)** — a CLI-side cache of `getWorkspaceDigest`, so an agent's cold first turn knows the ids without a round-trip and can grep the file (an MCP response is all-or-nothing). `cli/src/lib/map.js` + `rpc.js` (one stateless JSON-RPC POST; the endpoint needs no `initialize` first). Non-obvious parts: the **digest itself emits the cursor** (`getChangeHeadCursor` → `computeChangeVersion`, taken BEFORE the item queries so a concurrent write cannot fall between map and delta — do not move cursor generation into the CLI); `get_changes_since` now returns `nextCursor` **always**, and `settledCursor` keeps the id half `''` while the cursor's second is still within `HOT_SECOND_MS` of now (re-report once rather than miss) and switches it to `'~'` (above every uuid) once that second can no longer receive writes, so an idle poll returns empty instead of replaying forever. The bridge (`cli/src/commands/mcp.js`) refreshes at start-up and after each successful write, debounced 1.5s, learning write tools from `tools/list` `annotations.readOnlyHint === false` — a refresh failure is one stderr warning, never a failed tool call and never a byte on stdout. Git-ignored by default via the single `ignorePatternsFor` list in `map.js` (shared by `init`/`join`/`sync`, so no writer can drop another's pattern); `remnus sync --track` stores `trackMap: true` in the committed `config.json`. The `AGENTS.md` block is the contract agents actually read: **map → delta → targeted read → search last.**
- **Audit retention (`PlanLimits.auditDays`, enforced 2026-09-23)** — a VIEW, not a delete: `auditVisibleSince`/`activityAtOrAfter`/`activityVisibleIn` (services/auditRetention.ts) hide rows older than the workspace billing owner's plan on the four customer audit surfaces (`queryAuditLog`, `remnus://audit-log/recent`, `getUserAgentActivity` per-workspace, dashboard `activity` block). Physical deletion only past `AUDIT_HARD_RETENTION_DAYS` = 400 in the daily `/api/cron/recurrence` run, upserting savings into `agent_savings_rollup` in the SAME libsql batch. Never window the savings card 7/30-day figures, onboarding or admin funnels. A new audit surface must apply the window; the rollup condition must stay identical to getAgentMetrics' saved query.
- **Agent savings metrics (P5, synced here 2026-09-23)** — `services/agentMetrics.ts`: a baseline is MEASURED or NULL, never estimated (`agent_activity.baseline_bytes`, migration 0049). Saved = max(baseline − response, 0), all time (+ rollup); recalled items 30d, agent writes 7d, p50 30d. The card renders nothing while savedBytes = 0 — that is intended. Never show money or hours saved. Details: AGENTS.md → Agent Savings Metrics.

Hand-applied migrations are not tracked anywhere else; notes claiming "applied" were wrong for local on 2026-09-23.

A second run extends only (never a second database/page per concept, never overwrite a body it did not write, never delete — `add_comment`). - **Agents read wiki pages raw** (2026-09-23, P9.5): `/wiki/<slug>.md` serves the file; keep plain relative `.md` links in `docs/mcp/*.md` (the raw route makes them `/wiki/x.md`, HTML makes them `/wiki/x`, GitHub resolves them as-is). A new public cookie-less path under the intl middleware needs the `proxy.ts` matcher exclusion, not only `auth.config.ts`.
- **Page links in written content** are `<a data-page-link href="/page/<id>">` (`/db/<dbId>[/<rowId>]`) — the only form `extractPageRefs` records. Any agent-facing doc that tells agents to link must show that form; `[[Title]]` is plain text.
- **Select/status options**: services accept `value`/`name`/`label` and group aliases, and throw on an option without text or an unknown group (`autoColorOptions`). Never coerce an object with `String()` into stored data.
- **Recurrence on the MCP surface** — writes: `create_page`/`update_page` take a flattened `recurrence`; on `update_page` a row that already repeats REQUIRES `recurrenceScope`, and the call is refused with per-scope impact counts otherwise (an agent must not silently decide whether the user's past cards get rewritten). Reads: `get_page`/`get_pages` carry a full `recurrence` block; `query_database` rows carry only `recurring: true` — a rule per row would cost ~25 tokens × page size. OKF export nests the rule under `x-remnus.recurrence`; OKF **import does not** rebuild series because the importer flattens everything into one generic Concepts database with no date column, so there is nothing to hang a rule off.
- **Recurring calendar cards — every row-delete path must EXDATE.** `exdateOccurrenceForPage` runs in BOTH `actions/page.ts` `deletePage` and `services/workspace.ts` `deleteItemFromWorkspace` (MCP). Skipping it means the next materialization recreates the row (a date the rule calls for with no card on it IS the create signal), so the delete silently undoes itself. Any new row-delete path needs it.
- **Recurring calendar cards (0043)** — never regress these two invariants: past occurrences are never rewritten (a rule change SPLITS the series via `splitSeriesAt`, it does not mutate the rule), and an occurrence carrying user work is detached and kept, never deleted, unless the user explicitly ticked "delete cards with content too". Occurrences are real `pages` rows; do NOT reintroduce a virtual-expansion shortcut. Recurrence state lives in dedicated `pages` columns, never in `properties` (it would leak into Table columns/exports/filters/MCP row reads). Materialization is horizon-bounded (`max(today+90d, visible window+7d)`, 500/series cap) and idempotent via the UNIQUE (series_id, occurrence_date) index. The expansion engine is windowed by design — there is no "expand everything" call, because `{freq:'daily', end:'never'}` has no last occurrence. `npm run test:recurrence` guards the month-length/leap-year/COUNT-vs-EXDATE/weekend-shift edge cases plus the non-terminating-rule budget.
- **In-app changelog is agent-authored, not a CMS** — any user-visible change must add an entry to `src/lib/changelog.ts` in the SAME change, unprompted (rule in `AI.md` → `## Changelog / What's New`, echoed in `CLAUDE.md`). One sentence, customer language, newest first, all 8 locales (`Record<Locale,string>` makes a missing one a `tsc` error). Never rewrite a shipped `id` — the `remnus_whatsnew_seen` cookie stores it and changing it re-flags the entry as unread for everyone.
- New migrations: `when` value must be greater than all existing — next migration `when > 1782100000000`. 0039_knowledge_context adds canonical knowledge metadata, exact-revision human reviews, workspace context policy, and short-lived context runs; apply script is idempotent and has run on local + production Turso.
- **createdAt/updatedAt gotcha is NOT DrizzleAdapter-specific — it's plain SQLite:** a column `DEFAULT CURRENT_TIMESTAMP` evaluates to TEXT (`'YYYY-MM-DD HH:MM:SS'`), not a Unix integer, no matter which driver inserts the row; any `integer(...,{mode:'timestamp'})` column left to that default reads back as `Invalid Date`. Found (2026-07) silently affecting every workspace_items/standalone_pages/databases/pages insert that omitted createdAt/updatedAt — fixed by stamping both explicitly with `new Date()` in services/workspace.ts, actions/workspace.ts, actions/page.ts, seed.ts. When reading these columns for anything time-sensitive (delta sync, sort-by-recency), guard with an `isValidDate()`-style check — older pre-fix rows still carry the bad TEXT value and should be treated as unknown/epoch, not thrown on.
  - **SQL-aggregate corollary (fixed 2026-07-10):** SQLite's type ordering ranks TEXT ABOVE INTEGER, so a bare `max(updated_at)` over a table holding even ONE legacy TEXT row returns that TEXT value and pins the aggregate there forever. This silently broke live refresh app-wide: the `changeVersion` aggregate (now `src/lib/services/changeVersion.ts`) became `Number('2026-06-06 11:58:15')` → `NaN` → JSON `null` → the client's `typeof v === 'number'` guard dropped every tick, so `router.refresh()` never fired and edits (esp. calendar) only appeared after a manual refresh. Verified on local.db: all 4 tables (workspace_items/standalone_pages/databases/pages) had TEXT rows and returned TEXT maxes. **Always write `max(case when typeof(col) = 'integer' then col else 0 end)`**, and guard numeric wire values with `Number.isFinite`, never `typeof === 'number'` (NaN is a number, and compares false against everything, wedging a monotonic-version loop shut instead of failing loudly).
- **`remnus_last_path` resume cookie is owner-tagged** (`<hmac(userId, AUTH_SECRET)>:<encodedPath>`, see `src/lib/server/lastPath.ts`). It survives sign-out, so the next user on the same browser inherited it; checking only that they *can access* the path is NOT enough — an admin can open every workspace and co-members can open each other's pages, so the previous user's location validated and resumed under the new account. `/app` honors it only when the tag matches. HMAC (not the raw id) so a cookie left in a shared browser can't disclose or be forged against another account.
- Many recent migrations (0017–0038) are NOT in `_journal.json` — applied manually via `src/db/apply-00xx-*.ts` scripts (libsql `batch()` silently no-ops DDL). Apply each to BOTH local (`DATABASE_URL="file:local.db" npx tsx ...`) and Turso (plain `npx tsx ...` reads `.env`). **The Turso target loaded from `.env` is production** — plain runs are prod operations.
- **tsx/ESM import-hoisting gotcha:** in tsx scripts that `import { db } from '@/db'`, a `dotenv.config()` CALL runs too late (imports hoist above it) → '@/db' initializes with DATABASE_URL unset and silently falls back to file:local.db. Fix: `import 'dotenv/config';` as the FIRST import (see backfill-page-links.ts). Raw createClient apply scripts are immune; command-line `DATABASE_URL=...` prefix always safe. This misdirected a "Turso" backfill (2026-07-07) and probably Faz 0's 0034 "Turso" apply (prod audit-log inserts silently failed from the cd5faa2 deploy until 0034 was actually applied to prod on 2026-07-07).

- **Direct-insert gotcha (same family as createdAt/updatedAt above):** `seed.ts` inserts rows straight into the DB (`db.batch`), bypassing every action-layer side effect (`syncPageLinks`, tombstones, etc.) those tables normally get on write. Found 2026-07-07: seed content with a real childBlock link never entered `page_links` because `createRichWorkspaceData` never called `syncPageLinks()` — fixed by adding one explicit call after the batch insert. When adding a new write side-effect to an action, check whether `seed.ts` (or any other direct-DB-insert path) also needs it.

## Share inheritance (`shared_pages.created_by`) — fixed 2026-09-22
- A page created under a publicly shared parent MUST get its own `shared_pages` row: the public `/share/[...slug]` tree is built only from items that have one, so an unshared child is invisible to visitors.
- `shared_pages.created_by` is a **NOT NULL FK onto `user`**. The MCP paths (`autoShareIfParentShared` + `createPagesInWorkspaceBulk` in services/workspace.ts) used to write `agentCtx?.tokenId ?? 'system'` there — a token id, not a user id — so the (best-effort, error-swallowing) insert failed silently and agent-created sub-pages were NEVER published. Both now **inherit `created_by` from the parent share row**: always FK-valid, and ON DELETE CASCADE then retires the inherited subtree with the person who published it.

## Performance
- `Promise.all` for independent fetches (no waterfalls in layouts)
- Loading skeletons in `loading.tsx` files for each route
- **Bulk MCP writes are measured in STATEMENTS, not CPU** (Turso is remote; every statement is a network turn). `bulk_create_pages` → `createPagesInWorkspaceBulk` (services/workspace.ts): **5 round-trips regardless of batch size**, was ~7 per record. Rules a change here must keep (full list: AGENTS.md → Performance Rules → "Bulk write path"): ids generated up front with `crypto.randomUUID` so `ref`/`parentRef` resolves in memory; all per-entry validation done BEFORE the batch (so per-entry `ok`/`error` survives); `max(sort_order)` grouped, never a full row scan; explicit `new Date()` timestamps; multi-row inserts chunked via `chunkRows()` (services/sqlChunk.ts, 900 bind params); **side effects — `syncPageLinksBulk`, `recordGeneratedKnowledgeBulk`, inherited `shared_pages` — stay OUT of the content batch** (best-effort; a failing one must never roll back the pages it describes).
- `bulk_move_items` (sidebar mode) = 3 statements per call: every item shares one destination, so the ancestor chain used by the subtree guard is read once (recursive CTE, `depth < 100`).
- `bulk_delete_pages` is deliberately NOT batched: its snapshot → delete → tombstone → `purgeReferencesTo` → `removePageLinksFor` order is load-bearing (the purge finds its targets through the very `page_links` rows the next step drops), it recurses over descendants, and it already runs concurrently.

## Live refresh (rebuilt 2026-09-21) — see AGENTS.md → "Live refresh (the change signal)"
- There is NO server push. `src/lib/realtime/publish.ts` was a no-op (an in-memory EventEmitter
  can't fan out across Vercel's multi-instance runtime); it and its 45 call sites were deleted.
  Don't reintroduce a `publish()` that does nothing — the next reader will think it's live.
- `computeChangeVersion` MUST include the `deleted_items` tombstone aggregate. Without it a
  delete LOWERS `max(updatedAt)` instead of raising it, so removals never refreshed anything.
  Tombstones are insert-only, which is also what keeps the version monotonic.
- It's emitted as ONE `unionAll` statement, not N awaited queries: at a 2.5s poll the Turso
  round-trips are the cost, not the aggregates.
- `GET /api/activity/changes` is the fast, read-only half; `POST /api/activity/ping` writes a
  `user_sessions` row on every call and must never run at the fast cadence. Keep the changes
  response ~20 bytes — the whole mechanism exists because a 10s `router.refresh()` poll
  (~100 KB RSC payload per tick) was the dominant Vercel Fast Origin Transfer cost.
- Cadence invariant: an IDLE normal tab still costs exactly one request per 30s. Fast polling
  is only for a project window (flat 2.5s while visible) or a normal tab within ~90s of an
  observed change (1.6× backoff, then it stands down entirely).
- Deferring a refresh is about not resetting a caret/selection, nothing else. Use the shared
  `src/lib/interactionGate.ts` (held pointer / keystroke <1.5s / editable focused with a
  keystroke <15s). Never gate on `mousemove`: the 10s idle timer it replaced meant a human
  watching an agent work deferred refreshes indefinitely just by holding the mouse (40s+ worst
  case). `useWorkspaceEvents` and `TabHost` both use this one gate.

## Joining a connected project (`npx remnus join`)
- **A workspace id is not a credential.** It lives in a committed `.remnus/config.json`, so
  everyone with a clone has it. Re-read membership from the database on every render AND
  again inside every action; the URL/form value is always client input.
- **A non-member must learn nothing** about a workspace — not its name, not its members, not
  whether it exists. `createAccessRequest` returns the same `pending` for an id matching no
  workspace (nothing is stored), and a non-`connected` install-poll payload carries the
  *project* name, never the workspace's. Anything else turns this into an enumeration oracle.
- **Do not widen `mintAgentToken`.** It is owner-only and the AI Agents panel mints there.
  `join` uses `mintProjectAgentToken`, a separate export sharing the private `issueAgentToken`
  (row + funnel capture + first-agent email). Loosening a shared gate is how an escalation ships.
- **Clamp scope by role, and refuse rather than downgrade.** A `viewer` asking for write gets
  `Errors.viewerCannotWrite`, so the CLI can explain it instead of writing a credential that
  fails on first use.
- **Each join revokes this person's previous token for this project** (workspace + `created_by`
  + the `Remnus CLI · <project>` name), *before* `checkCanAddAgent` — otherwise a re-join is
  blocked by the slot it is about to free. `countAgents` counts every un-revoked PAT and every
  join mints one. Tell the human; never drop a session silently. **Open question: the quota is
  per token, not per person** — one human on three machines still costs three agent slots.
- **A request costs nothing; an approval costs a seat.** `checkCanAddSeat` runs at approval
  time, inserts as `member` (never the requested scope, never owner), and a refusal leaves the
  request PENDING so the owner can free a seat and approve the same row.
- **`join` writes exactly one file**: `.remnus/credentials.json`. Never `config.json` (its
  `calibrated` flag above all), the `AGENTS.md` section or `.claude/settings.json`. It fills a
  *missing* `.mcp.json` entry or `.gitignore` block but never overwrites one. `git status`
  after a join must be clean — that is the assertion worth keeping a test for.
- **`init` on an already-connected project joins it.** Reconnecting needs `--reconnect`:
  silently re-pointing a committed config forks a team's shared memory, and nobody notices
  until both halves have content.
- Recovery advice must name `join`, not `init`, wherever the project is connected and only the
  credential is missing (`mcp.js` 401/403 + missing-token, `doctor`'s no-token branch).
